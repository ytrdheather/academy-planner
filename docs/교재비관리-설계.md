## 0. 한 줄 요약

교재 변경 신청 → 원장 승인 → 학부모 알림톡 발송 → 입금 확인까지를 **노션 DB 한 개**로 모으고,
Make 시나리오를 걷어내 **Render 서버의 크론 한 개**가 상태 전이를 전부 처리하게 한다.

**2권 제한의 정체 (실물 확인 완료)**: 별도 신청 DB가 있는 게 아니라, 교재 변경 워크플로 전체가
**학생 명부(속성 78개) 안에 컬럼으로 박혀 있다.** `새교재1`·`새교재2` **relation 슬롯 두 개**가
전부이고, 거기에 롤업 4개(`교재1 이름`/`교재1 가격`/`교재2 이름`/`교재2 가격`)와
수식 2개(`알림톡용_교재명`/`알림톡용_합계금액`)가 붙어 있다.
3권째를 넣으려면 relation·롤업·수식·Make 매핑·알림톡 템플릿을 전부 새로 만들어야 한다.

→ **relation 하나(다중)로 바꾸면 개수 제한이 원천적으로 사라진다.** 이것이 이번 설계의 핵심.

| 교재 마스터 `교재 데이터 베이스` | `TEXTBOOK_DB_ID` | `18f09320bce2800aac09c7856bf17e7d` | 속성 10개 / 교재 552권 |

> 두 DB 모두 부모가 `block_id` 다 — 페이지 본문 안에 인라인으로 박힌 DB 라는 뜻이고,
> 그 블록은 통합에 공유돼 있지 않다. **그래서 API 로 "같은 위치"에 새 DB 를 만들 수 없다.** (§12 참조)

> ⚠️ **교재 마스터는 절대 구조를 바꾸지 말 것.** 진도 자동화가 `교재이름`·`총유닛수`·`유닛당지문수`·`워크북`과
> 교재 세부 내용 DB relation에 물려 있다. 여기를 손대면 숙제 자동 배정이 같이 무너진다.
> 이번 작업은 교재 마스터를 **읽기만** 한다.

### 1-1. 교재 마스터 — 가격 체계 (실측)

| 속성 | 타입 | 값 |
|---|---|---|
| `교재이름` | title | |
| `과목` | select | 노트·애니더빙·리스닝·독해서·어휘서·문법서·파닉스·내신용 |
| **`가격`** | **number** | **정가** (예: 16,000) — ✅ 속성 이름 `가격` 확정 |
| **`안내가`** | **formula** | **`floor(가격 × 0.9)`** = 학부모에게 실제로 안내되는 **10% 할인가** |
| `숫자` | number | 552권 중 354권이 빈값. 용도 불명 — **쓰지 않는다** |
| `총유닛수`·`유닛당지문수`·`워크북`·`URL`·`텍스트` | | 진도 자동화용. 건드리지 않음 |

**🔴 가장 중요한 발견 — 할인은 "권당"이 아니라 "합계에 한 번" 적용된다.**

현행 `알림톡용_합계금액` 수식이 실제로 하는 계산은 `floor(가격합계 × 0.9)` 이다. 실측 검증:

| 학생 | 교재 정가 | 합계 | 현행 출력 |
|---|---|---|---|
| 김윤하 | 16,000 + 14,000 | 30,000 | `27,000원` = floor(30000×0.9) ✅ |
| 형단희 | 15,000 + 16,000 | 31,000 | `27,900원` = floor(31000×0.9) ✅ |
| 오시영 | 7,778 | 7,778 | `7,000원` = floor(7778×0.9) ✅ |

**새 DB에서 `안내가`를 롤업 합계하면 금액이 달라진다.** 권당 floor를 하기 때문이다.
(예: 7,778 + 11,112 → 합계 후 할인 = 17,001원 / 권당 할인 합계 = 17,000원)
→ **반드시 `가격`을 sum 롤업한 뒤, 수식에서 한 번만 `floor(×0.9)` 할 것.** §3-2 참조.

**🟡 `가격` 칸에 역산 값이 섞여 있음.** `7778`, `11112` 같은 값은 원하는 안내가(7,000 / 10,000)를
만들려고 정가를 거꾸로 계산해 넣은 것으로 보인다. 정가가 진짜 정가가 아니게 되어 있다.
새 설계에서는 `가격`에 실제 정가를 넣고 예외는 `조정 금액`으로 처리하는 것이 맞지만,
**기존 552권을 정리할지는 원장 판단.** 지금 방식 그대로 둬도 금액 계산은 맞게 나온다.

**🔴 552권 중 197권(36%)이 `가격` 비어 있음.** 과목별 분포:

| 과목 | 전체 | 가격없음 | 비율 | 판단 |
|---|---|---|---|---|
| 애니더빙 | 65 | 65 | 100% | 판매 대상 아님 — 정상 |
| **문법서** | **123** | **71** | **58%** | 🔴 **실제 판매 교재인데 절반 이상 누락** |
| 독해서 | 287 | 39 | 14% | 🟡 확인 필요 |
| 파닉스 | 20 | 5 | 25% | 🟡 |
| 리스닝 | 10 | 3 | 30% | 🟡 |
| 내신용 | 3 | 1 | 33% | 🟡 |
| 어휘서 | 31 | 1 | 3% | 정상 |
| (과목없음) | 12 | 12 | 100% | 🔴 **이름도 비어 있는 빈 행 = 쓰레기 데이터. 삭제 대상** |

**가격 없는 교재를 고르면 그 권은 조용히 0원으로 합산되어 학부모에게 적게 청구된다.**
→ 발송 전 검증을 반드시 넣는다. §6-2 참조.

## 2. 신설: 교재비 관리 DB — ✅ 2026-08-04 생성 완료 (21개 전부)

### 🔴 여기서 "1건"은 교재 1권이 아니다 — 변경 신청 1회다

**1행 = 학생 1명의 교재 변경 1회.** 그 한 번에 교재가 몇 권이든 **전부 같은 행에 담는다.**

- 입학하면서 4권을 받는다 → **한 행.** `변경 교재` 에 4권을 넣는다. 문자 한 통.
- 한 주에 3권을 바꾼다 → **한 행.** 문자 한 통.
- 교재 1권당 한 줄씩 만드는 게 **아니다.** 그러면 학부모가 문자를 네 통 받는다.

`변경 교재` relation 은 **개수 제한이 없다.** 애초에 학생 명부의 `새교재1`·`새교재2` 슬롯 2개
제한을 없애려고 이 DB 를 만든 것이다(§0). 실측: 교재 3권을 한 행에 넣으니
`교재 목록` = `"60-Word Reading 2, 60-Word Reading 1, 50-Word Reading 2"`, `청구 금액` = `43200` 한 줄로 나왔다.

> ⚠️ **`single_property` 라는 이름에 속지 말 것.** relation 3개가 전부 `single_property` 인데,
> 이건 "한 개만 연결된다"는 뜻이 **아니라** 상대 DB 에 역방향 컬럼을 안 만든다는 뜻이다(§1 보호).
> 연결 개수는 무제한이다.
>
> 다만 **`학생` relation 에만** UI 에서 "페이지 1개로 제한"을 켠다. 한 행은 학생 한 명 것이어야
> 하기 때문이다. **`변경 교재`·`기존 교재` 에는 절대 켜지 말 것.**

### 2-1. 학생 이름은 어디에 쓰나 — **어디에도 타이핑하지 않는다**

선생은 `학생` relation 에서 **학생 명부의 학생을 고를 뿐이다.** 이름을 손으로 적는 칸은 없고,
있어서도 안 된다(§3-1 이 교재명을 relation 에서 뽑는 것과 같은 이유 — 타이핑하면 오타가 난다).

**이름 전용 컬럼(롤업)은 두지 않는다.** 노션 relation 컬럼은 연결된 페이지의 title(=`이름`)을
칩으로 그대로 보여주므로, 이름 롤업을 따로 만들면 같은 이름이 두 번 보이는 중복 컬럼이 된다.
(2026-08-04 에 `학생 이름` 롤업을 만들었다가 이 이유로 도로 지웠다. 다시 만들지 말 것.)

`제목`(title)은 서버가 `김서연 · 2026-08-04` 로 채운다. 선생이 행을 만든 직후엔 비어 있지만,
`학생` 칩에 이름이 보이므로 원장이 승인할 때 누구 건지 헷갈리지 않는다.

- 서버는 `제목` 을 `승인대기` 처리(크론 1번)할 때 함께 채운다. **relation 은 API 로 읽으면 `[{id}]`
  만 오고 이름은 안 온다**(§8). 그래서 `GET /v1/pages/{학생id}` 를 한 번 쳐서 이름을 가져온다.
  행 몇 개짜리라 호출 하나 늘어나는 건 문제되지 않는다.
- 이름이 바뀌어도 **이미 채워진 `제목` 은 안 따라온다.** 이건 의도한 것이다 —
  발송 당시의 기록이라 그대로 남는 편이 맞다.

## 3. 수식 2개

### 3-1. `교재 목록` (문자용 텍스트) — ✅ 적용됨

**선생이 교재 이름을 손으로 옮겨 적는 단계는 두지 않는다.** 거기서 반드시 오타가 나고,
오타 난 교재명이 그대로 학부모에게 나간다. relation에서 자동으로 뽑는다.

**실제로 들어간 식:**

```
format(prop("변경 교재"))
```

실측 출력: `"60-Word Reading 2, 60-Word Reading 1, 50-Word Reading 2"`

> 🔴 **원안 `join(map(prop("변경 교재"), current.name), ", ")` 는 API 로 못 넣는다.**
> `400 validation_error: Type error with formula` — API 수식 파서가 `current` 를 모른다.
> `current.prop("교재이름")` 도, 메서드 체인 `.map().join()` 도 같은 이유로 거부된다.
>
> 🔴 **`join(prop("변경 교재"), ", ")` 는 저장은 되는데 출력이 `","` 다.** 조용히 틀리는 쪽이라
> 더 위험하다. 저장 성공만 보고 넘어가면 학부모에게 교재명 없이 쉼표만 나간다.
> **수식은 반드시 테스트 행을 만들어 출력값까지 확인할 것.**
>
> `format(관계)` 은 노션이 내부적으로 `join(map(..., current.name), ", ")` 으로 펼쳐 준다.
> 즉 원안과 같은 계산이고, 구분자도 `", "` 라 §5(줄바꿈 금지)에 맞는다.

- 수식 속성 값은 Notion API로 그대로 읽히므로 Solapi에 바로 넣을 수 있다.
- 이 수식의 구분자는 쉼표(`, `)다. **원장·담당쌤 카카오워크 알림에는 이걸 그대로 쓴다.**
- 🔴 **학부모 알림톡은 다르다.** 서버가 relation 에서 교재 이름을 직접 읽어 **한 줄에 한 권**으로
  다시 만든다(2026-08-05). 쉼표로 이어붙이면 5권부터 문단처럼 뭉쳐서 못 읽는다 — 실물로 확인했다.
  **이 수식 문자열을 `", "` 로 쪼개서 쓰지 말 것.** 교재명에 쉼표가 들어 있으면 엉뚱하게 잘린다.
  가격 검증하느라 어차피 교재 페이지를 하나씩 읽으므로 거기서 이름을 같이 모은다.

### 3-1-a. `기존 교재 목록` — ✅ 추가됨 (원장 승인 알림 전용)

```
format(prop("기존 교재"))
```

실측 (기존 2권 → 변경 3권):

```
기존    60-Word Reading 2, 60-Word Reading 1
변경    50-Word Reading 2, 50-Word Reading 1, 40-Word Reading 2
```

**원장이 승인 판단을 하려면 뭘 뭘로 바꾸는지 봐야 하므로 카카오워크 알림에는 둘 다 싣는다.**
반대로 **학부모 알림톡에는 변경 교재만 나간다** — 이유는 §5.

### 3-2. `청구 금액` — 🔴 할인 적용 순서 주의 (✅ 적용됨, 실측 검증 완료)

`합계 금액` 롤업은 **`안내가`가 아니라 `가격`(정가)을 sum** 해야 한다.
그리고 **10% 할인은 합계에 딱 한 번** 적용한다. 현행 시스템과 동일한 계산을 유지하기 위해서다(§1-1).

```
floor((prop("합계 금액") + if(empty(prop("조정 금액")), 0, prop("조정 금액"))) * 0.9)
```

- `안내가`를 sum 하면 권당 floor가 먹어서 금액이 1~2원씩 달라진다. **하지 말 것.**
- `조정 금액`이 비면 전체가 빈값이 되는 것을 막는 방어가 `if(empty(...))`.
- 할인율 0.9가 바뀔 수 있으므로 이 수식 위치를 문서에 기억해 둘 것.
- 노션 수식 편집기에서 실제 숫자가 나오는지 반드시 눈으로 확인.

> **금액 콤마(27,000원)는 노션 수식에서 하지 말 것.** 서버가 `Number(x).toLocaleString('ko-KR')`로
> 포맷해서 문자에 넣는다. (현행 `알림톡용_합계금액` 수식이 `replaceAll`을 겹쳐 쓰며 콤마를 만드는데,
> 읽기도 고치기도 어렵다. 서버로 옮긴다.)

### 3-3. `조정 금액`을 두는 이유

노션 relation은 **같은 페이지를 중복으로 못 담는다.** 같은 교재 2권(형제 동시 수강, 분실 재구매)은
relation으로 표현이 안 되므로 `조정 금액`에 차액을 직접 적어 보정한다. `요청 메모`에 사유를 남긴다.

정가가 없는 교재(§1-1의 197권)를 급히 내보내야 할 때도 여기로 보정할 수 있다.
다만 **원칙은 교재 마스터의 `가격`을 채우는 것**이고, `조정 금액`은 예외 처리용이다.

## 4. 진행상태 (select) 와 상태 전이

옵션(실제 생성됨): `작성중` → `승인대기` → `승인됨` → `발송중` → `발송완료` / `반려` / `보류`

| 상태 | 누가 바꾸나 | 의미 |
|---|---|---|
| `작성중` | 선생 | 교재 고르는 중. 서버는 무시 |
| `승인대기` | **선생** | 신청 완료 → 서버가 원장에게 카카오워크 |
| `승인됨` | **원장** | 서버가 담당쌤에게 카카오워크. 조교 장보기 목록에 뜸 |
| `반려` | 원장 | `반려 사유`와 함께 담당쌤에게 카카오워크 |
| `보류` | 서버만 | 가격 미입력 교재가 섞여 있어 발송을 멈춘 건 (§6-2). 가격 채운 뒤 `승인됨`으로 되돌리면 다시 나간다 |
| `발송중` | 서버만 | 발송 직전 선점 표시 (§6) |
| `발송완료` | 서버만 | `발송 일시` 기록됨 |

**사람이 만지는 상태는 `승인대기`·`승인됨`·`반려` 셋뿐이다.** 나머지는 서버가 관리한다.

### 크론 1개가 도는 한 바퀴 (5분 주기)

```
1) 진행상태=승인대기 AND 원장알림함=false
   → 원장 카카오워크 발송 → 원장알림함=true

2) 진행상태=승인됨|반려 AND 교사알림함=false
   → 담당쌤 카카오워크 발송 → 교사알림함=true

3) 진행상태=승인됨 AND 발송예약=true
   → 진행상태=발송중 으로 먼저 변경(선점)
   → 알림톡 발송 (실패 시 LMS 폴백)
   → 진행상태=발송완료, 발송일시=now, 발송예약=false
```

이 세 줄이 지금 Make 시나리오 전체를 대체한다.

### 변수 3개 ↔ 우리 DB 매핑

**학부모에게는 변경 교재와 총액만 나간다** (2026-08-05 원장 확정).

  합이 청구액과 1~2원 어긋난다. 예: `7,000 + 10,000 = 17,000` 인데 실제 청구는 `17,001`.
  가격 미입력 교재 197권이 `0원`으로 노출되는 문제도 겹친다.
- `#{교재비}` 는 **`43,200원` 형태 그대로.** 할인 문구("정가 48,000원 · 10% 할인")를 붙이는 안도
  검토했으나 넣지 않기로 했다.

### 🔴 이 템플릿을 쓰기 때문에 생기는 제약

1. **계좌가 본문에 하드코딩돼 있다.** 계좌가 바뀌면 **템플릿을 다시 심사받아야 한다.**

3. **길이는 문제없다.** 고정 161자 + 변수, 알림톡 상한 1,000자.
   교재명 평균 20자 기준 **40권까지 들어간다.**

## 6. 반드시 지킬 것 — 중복 발송 방지

**이 시스템에서 가장 나쁜 사고는 학부모가 같은 안내를 두 번 받는 것이다.** 입금 요청이라 더 그렇다.

크론이 겹쳐 돌거나 배포 중 재시작되면 같은 행을 두 번 집을 수 있다. 그래서:

1. 발송 **직전에** `진행상태`를 `발송중`으로 먼저 PATCH 한다
2. 그 PATCH가 성공한 행만 실제로 발송한다
3. 발송 후 `발송완료` + `발송 일시` 기록

`발송중`에서 30분 넘게 멈춘 행은 발송 실패로 보고 원장에게 카카오워크로 알린다.
(조용히 안 나가는 것도 두 번 나가는 것만큼 나쁘다.)

### 6-2. 🔴 발송 전 필수 검증 — 가격 누락 교재

교재 552권 중 **197권에 `가격`이 비어 있다**(§1-1). 문법서는 절반 이상이다.
가격 없는 교재를 relation에 담으면 **롤업 합계가 그 권을 0원으로 조용히 무시**하고,
학부모에게 실제보다 적은 금액이 청구된다. 나중에 차액을 다시 요구해야 하는데,
이건 학원 신뢰가 걸린 문제라 반드시 발송 전에 막아야 한다.

발송 크론은 각 행에 대해 **발송 직전에** 이렇게 검사한다:

```
0) 변경 교재가 0권이면
   → 발송하지 않는다 (알림톡은 변수가 빈 문자열이면 카카오가 거부한다, §5)
   → 진행상태를 '보류', 원장에게 카카오워크: "김서연 건 — 변경 교재가 비어 있음"
1) 변경 교재 relation의 각 교재 페이지를 읽는다
2) 가격이 null 이거나 0 인 교재가 하나라도 있으면
   → 발송하지 않는다
   → 진행상태를 '보류'로 바꾸고
   → 원장에게 카카오워크: "김서연 건 발송 보류 — 'Grammar Inside 2' 가격 미입력"
3) 전원 정상일 때만 발송
```

**원장이 승인 화면에서 미리 알 수 있게 하는 것이 더 낫다.** 승인 대기 알림에도
가격 누락 교재를 함께 실어 보내면, 승인 시점에 교재 마스터를 고칠 수 있다.

> 장기적으로는 **문법서 71권의 가격을 채우는 것**이 근본 해결이다. 이건 사람이 해야 하는 일이라
> 시스템으로 대신할 수 없다. 다만 `과목=문법서 AND 가격 비어있음` 뷰를 노션에 하나 만들어 두면
> 틈틈이 채워 나가기 쉽다.

## 7. 조교용 장보기 목록 — 이 DB만으로는 안 되는 유일한 것

학부모는 **학생별**로 받아야 하지만 조교는 **교재별**로 산다.
한 행에 5권이 묶여 있으면 노션에서는 "이번 주에 Reading Sense 3을 몇 권 사야 하나"가 나오지 않는다.

DB를 쪼갤 필요는 없다. 서버가 `진행상태=승인됨 AND 구매상태≠구매완료`인 행을 전부 읽어
교재별로 합산한 페이지 한 장을 뽑아준다:

```
GET /api/textbook/shopping-list

Reading Sense 3      4권   김서연 이준호 박민서 최유진
Word Master 중등2    2권   김서연 이준호
Grammar Inside 2     1권   박민서
```

조교 업무를 제일 크게 줄이는 것이 이 한 장이다. Phase 3에서 만든다.

## 8. Notion API 읽기 참고 (서버 구현용)

속성 타입별 JSON 모양. 여기서 실수가 제일 많이 난다.

| 타입 | 읽는 법 |
|---|---|
| title / rich_text | `p['제목'].title[0]?.plain_text` — 기존 `noticePlainText()` 헬퍼 재사용 |
| relation | `p['변경 교재'].relation` → `[{id}, …]` — **이름은 안 옴. 페이지를 따로 읽어야 함** |
| rollup(합계) | `p['합계 금액'].rollup.number` |
| rollup(원본) | `p['학부모 연락처'].rollup.array[0]?.phone_number` |
| formula(문자) | `p['교재 목록'].formula.string` |
| formula(숫자) | `p['청구 금액'].formula.number` |
| select | `p['진행상태'].select?.name` |
| checkbox | `p['발송 예약'].checkbox` |
| phone_number | `p['전화번호'].phone_number` |

> `교재 목록` 수식이 있으므로 **relation을 풀어 교재 이름을 조회할 필요가 없다.** 수식 문자열을 그대로 쓴다.
> 장보기 목록(§7)만 relation을 풀어야 하는데, 교재 마스터를 한 번 통째로 읽어 `{id: 이름}` 맵을 만들어 두면 된다.

## 10. 학생 명부에서 걷어낼 속성 (2026-08-04 실측)

교재 변경 워크플로가 학생 명부 안에 컬럼으로 들어가 있다. 새 DB로 옮기면 아래 **19개가 불필요**해진다.
학생 명부 속성이 78개 → 59개로 줄어든다.

| 속성 | 타입 | 새 DB에서 대체되는 것 |
|---|---|---|
| `새교재1` / `새교재2` | relation | → `변경 교재` (다중, 무제한) |
| `교재1 이름` / `교재2 이름` | rollup | → `교재 목록` 수식 |
| `교재1 가격` / `교재2 가격` | rollup | → `합계 금액` 롤업 |
| `알림톡용_교재명` | formula | → `교재 목록` |
| `알림톡용_합계금액` | formula | → `청구 금액` + 서버 포맷 |
| `현재교재` / `현재교재이름` | relation / rollup | → `기존 교재` |
| `변경희망교재` / `변경희망교재이름` | relation / rollup | → `변경 교재` |
| `승인상태` | select | → `진행상태` |
| `교재원장알림발송` | checkbox | → `원장알림함` |
| `교재안내 발송체크` | checkbox | → `발송 예약` |
| `교재코멘트` | rich_text | → `요청 메모` |
| `MSG1` / `MSG2` / `알림톡 메세지` | rich_text | → 서버가 조립. 노션에 저장하지 않음 |

> ⚠️ **삭제는 새 시스템이 2~3주 안정적으로 돌아간 뒤에 한다.** 노션은 속성을 지우면 값이 같이 사라지고,
> 다른 뷰·수식이 그 속성을 참조하고 있을 수 있다. 지우기 전에 `완료한 교재 리스트`처럼
> **남겨야 할 relation과 헷갈리지 않도록** 하나씩 확인할 것.
>
> `주독해교재`·`부독해교재`·`어휘교재`·`영어 더빙 OR 듣기 교재`·`완료한 교재 리스트`는
> **진도 자동화가 쓰는 속성이므로 절대 건드리지 않는다.**

### 10-1. 현재 데이터 상태 — 이관 전 정리 대상

재원생 88명 기준 `승인상태` 분포:

| 값 | 인원 | 조치 |
|---|---|---|
| (비어있음) | 55 | — |
| **대기** | **31** | 🔴 **처리 안 되고 쌓인 건. 이관 전에 원장이 훑어야 함** |
| 검토중 | 2 | 🟡 확인 필요 |

- select 옵션에 `승인요청`·`변경승인`·`승인`이 정의돼 있지만 **아무도 쓰지 않는다.** 상태가 5개인데
  실제로는 2개만 굴러가고 있다는 뜻이다. 새 DB의 `진행상태`를 6개로 잡되, 사람이 만지는 건
  `승인대기`·`승인됨`·`반려` 셋뿐이라는 원칙을 지킬 것(§4).
- **`새교재1`이 채워져 있는데 `승인상태`가 비어 있는 학생이 여럿 있다.** 데이터와 상태가 따로 논다.
  덮어쓰기 구조(학생 1명 = 1건, 이력 없음)라 지난 건인지 이번 건인지 구분이 안 된다.
- `교재원장알림발송`·`교재안내 발송체크`·`MSG1`·`MSG2`·`알림톡 메세지`는 전원 비어 있다.
  Make가 발송 시점에 채우고 지우는 것으로 보인다.

**이관 방식**: 자동 마이그레이션을 만들지 않는다. 대기 31명은 어차피 원장이 한 번 훑어야 하고,
그 김에 새 DB에 손으로 넣는 편이 빠르고 안전하다. 스크립트를 쓰면 위 "상태와 데이터가 따로 노는"
행들을 잘못 해석해서 엉뚱한 금액이 학부모에게 나갈 수 있다.

### 10-2. 이 구조의 근본 문제 (새 DB가 해결하는 것)

학생 명부에 붙어 있으면 **학생 1명당 교재 변경 건이 동시에 하나만 존재할 수 있다.**

- 지난 학기에 무슨 교재를 얼마에 안내했는지 **이력이 남지 않는다** — 다음 건이 덮어쓴다
- `입금 확인`을 학생 행에 붙이면 **이번 건 입금인지 지난 건 입금인지 구분할 수 없다**
- "이번 달 교재비 매출", "미입금 명단" 같은 걸 뽑을 수 없다

새 DB는 1행 = 1건이므로 이력이 자연히 쌓이고, 위 세 가지가 전부 해결된다.
